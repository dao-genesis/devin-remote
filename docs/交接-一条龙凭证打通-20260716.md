## 一、用户的核心底层目标（最重要，一句话）

> **用户只输入「Cloudflare 账号+密码」或「GitHub 账号+密码+2FA 凭证」，插件后端就全链路
> 自动打通一切**：登录 → 建 Token → 建自有化 Worker 持久通道 → 落盘置顶 → 反向注入
> 端点与 MCP → 全部板块可用。**手机端、电脑端同一套逻辑**（都是前端能做的操作，底层必能自动化）。

关键约束（用户原话精神）：
1. **摒弃「低劣的浏览器自动化」**（playwright 驱动点按钮那种）。要走**官方 API / 授权协议**的
   底层实现，稳定、不易被风控。
2. **穷尽市面方案**：主动搜罗 Cloudflare / GitHub 官方 API、OAuth device flow、社区开源项目
   （wrangler、cloudflared、gh、workers-auth 等）的做法，择优落地。
3. **在实践中暴露缺陷 → 迭代优化**，直到最终目标达成。目标只有一个，链路一定要打通。

## 三、唯一卡点（要突破的底层）

**全自动「纯凭证 → 建新 Worker」的最后一环 = Cloudflare 登录页的 Turnstile 人机验证。**

现有两条路都留了「一次人工」：
1. `cred-login`（credlogin.mjs）：浏览器自动化填账密 → **被 Turnstile 挡**（用户明确不要这条低劣路径）。
2. `oauth-login`（oauth.mjs）：wrangler 公开 OAuth 应用 + PKCE，**只需用户点一次「授权」**——
   这已是「无手搓 Token」的正解，但仍有一次点击，且授权页前若未登录仍要过 Turnstile 登录。

> 用户要的是**连这一次点击/验证也从底层消掉**：只凭账密（或 GitHub 账密+2FA）后端全自动。

## 四、下一步：从底层突破的技术路线（给下一个 Agent）

**目标不是把浏览器自动化做得更强，而是找到不需要浏览器的官方/半官方 API 路径。** 建议穷尽调研并择优：

### A. Cloudflare 侧（账密 → Worker 通道）
1. **优先调研 Cloudflare 官方登录/令牌 API**：
   - `POST https://api.cloudflare.com/client/v4/...` 全系需要**已有 API Token/Key**（鸡生蛋问题）。
     突破口在「如何仅凭账密拿到第一个可编程凭证」。
   - 研究 CF Dashboard 私有 API（`dash.cloudflare.com/api/v4/...` 的 `/login`、
     `/memberships`、`/user/tokens`）：登录返回会话 cookie，再用会话调 `POST /user/tokens`
     **以编程方式创建 API Token**（等价于用户在前端点 Create Token）。**这才是「前端能做→后端也能做」
     的正解**。难点：登录接口有 Turnstile / 有时 CAPTCHA。调研点：
     - CF 是否对**受信任设备/已有会话**放行免验证码登录；
     - 是否可用**邮箱 OTP / API 化的 2FA** 走通登录换 cookie；
     - 参考 `cloudflare-python`/`cloudflare-go` SDK、社区 `cloudflare-api` 逆向项目的登录实现。
2. **wrangler OAuth device code flow**（若 CF 支持）：device flow 无回调端口、无浏览器嵌入，
   用户在**任意设备**输入 user_code 即可——比 localhost:8976 回调更贴合手机/远程场景。
   现有 `oauth.mjs` 用的是 authorization_code + PKCE（`CLIENT_ID=54d11594-...`），
   调研该 client 是否也允许 `urn:ietf:params:oauth:grant-type:device_code`。
3. **既有资产可直接复用**：`addons/dao-relay/{oauth.mjs,provision.mjs,worker.js,wrangler.toml}`
   已实现「令牌 → 部署 → 绑自定义域 → 健康检查 → 落盘 `~/.dao/relay.json`」全链路。
   **突破点只在「拿到令牌」那一步**，拿到后调 `provision(token)` 即完成。
   - `provision.mjs`：`token → firstAccountId → ensureSubdomain → wrangler deploy →
     tryCustomDomain → healthOk → saveState`。
   - PR#165 的 `rt-flow-app cf-provision` 已支持 **Global API Key(email+key)** 纯后端零浏览器建 Worker——
     **务必先读它的实现**（`git show f8ab42ba`），把同一套 email+key 路径下放到插件后端，
     很可能直接就是用户要的「账密→建 Worker」的最短路径（Global API Key 在 CF 前端「My Profile →
     API Tokens → Global API Key」可查，属于账户凭证范畴）。

### B. GitHub 侧（账密+2FA → 全链路）
1. **GitHub Device Flow（首选·无密码无浏览器自动化）**：
   `POST https://github.com/login/device/code` → 用户输入 user_code → 轮询
   `POST https://github.com/login/oauth/access_token` 拿 token。**天然规避密码/2FA 自动化**。
2. 账密+2FA → 编程创建 PAT：GitHub 已**弃用** Basic Auth 建 token 的 `/authorizations` API，
   故账密直建 PAT 不再可行；**应转向 Device Flow 或 GitHub App**。用户提供的账密+2FA 更适合
   用来**在 IDE 宿主浏览器登录态**下走 OAuth，而非后端模拟登录。
3. 主控文档（用户附件 `dao-genesis--*.md`）里**每个 GitHub 账号已带 PAT**（`ghp_*`）——
   现阶段 GitHub 舰队/MCP 可直接用这些 PAT，不必卡在「账密建 token」。

### C. 统一收口
- 拿到 CF token 后：`provision()` → `daoRelaySetPersistent(url)` → `connectRelay` 置顶 →
  `daoSyncDaoMcpIntoProfile()` 把新透明端点写入反向注入档案 → 全池重注入。
- 手机端（rt-flow-app）与电脑端（dao-vsix）**共用** `addons/dao-relay` 那套 provision/oauth，
  逻辑一致；打通一端另一端同理。
